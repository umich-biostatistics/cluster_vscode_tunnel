# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Three Bash scripts, no build system and no tests. They install the VSCode CLI as a private LMOD module on a SLURM cluster (University of Michigan Great Lakes) and submit batch jobs that run `code tunnel` on a compute node. They target the cluster (Linux, Lmod `ml`, `sbatch`), not the macOS/Linux workstation where they are edited, so they cannot be run end to end locally.

Useful checks locally: `shellcheck codetunnel initialize.sh vscode_tunnel.sh` and `bash -n <script>`.

## How the pieces fit together

- `initialize.sh [-gh|--github|-ms|--microsoft]` (run once, from a clone of this repo on the cluster; defaults to GitHub): writes `~/Lmod/vscode/vscode.lua`, downloads the CLI tarball into `~/software/vscode`, copies `codetunnel` there, writes `~/software/vscode/cluster_tunnel_config`, then runs `code tunnel user login --provider github|microsoft`.
- `codetunnel` is installed as a **copy** in `~/software/vscode` (on PATH via the module), so edits to the repo copy do not take effect until `initialize.sh` is re-run. It finds the repo by sourcing `cluster_tunnel_config` (next to the `codetunnel` found by `which`), which exports `CLUSTER_VSCODE_TUNNEL_DIR`, and falls back to resolving its own symlink-aware location. It uses that directory for `vscode_tunnel.sh` (existence check only) and for `logs/`.
- `codetunnel` does not use `vscode_tunnel.sh` as a template despite the existence check. It prompts for parameters, writes a fresh batch script to a `mktemp` file with a heredoc, and calls `sbatch` on it. SBATCH defaults live in the prompts in `codetunnel`; separate defaults live in the `#SBATCH` lines of `vscode_tunnel.sh` (manual submission path). Keep the two in sync when changing either.
- `vscode_tunnel.sh` is the standalone `sbatch` template for the manual path. The user edits `--account` (placeholder `ACCOUNT_HERE`) before submitting.

## Gotchas

- Every `code tunnel` invocation must run with `VSCODE_CLI_USE_FILE_KEYCHAIN=1` and `VSCODE_CLI_DISABLE_KEYCHAIN_ENCRYPT=1`: `initialize.sh` sets them inline on the login command, `vscode_tunnel.sh` exports them, and the batch script generated by `codetunnel` sets them inline on the `code tunnel` line. Keep all three in sync, and add them to any new `code tunnel` call.
- `codetunnel --update` and the weekly update notice talk to `update.code.visualstudio.com` for the `cli-alpine-x64` stable build, while `initialize.sh` downloads the same build from `code.visualstudio.com/sha/download`. Keep the platform in sync. The installed version is compared by the 40-hex commit hash parsed from `code --version`, so that output must keep containing it. The notice's cache is `.codetunnel_update_check` next to the `code` binary.
- The module name, `~/Lmod`, and `~/software/vscode` paths are hard-coded across `initialize.sh` (module file and install dir), `codetunnel` (`ml use ~/Lmod`), and `vscode_tunnel.sh`. Change them together.
- Job logs go to `<repo>/logs/%x-%J.out` (`logs/` is gitignored). The log path that `codetunnel` prints assumes `--output` uses the job name and job ID.
- `vscode_tunnel.sh` uses a relative `--output=logs/...`, so it must be submitted from the repo root with `logs/` already created (`mkdir -p logs`). Only `codetunnel` creates the directory and uses an absolute path.
- The README documents the user-facing prompts and example output; update it when prompts or defaults change.
